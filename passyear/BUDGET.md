## 09-04 成本模型修正 ②：token 不等价（用户指正）

上一节把 input / cache / output 按同一价格算，**错了**。实际倍率（相对未命中 input = 1）：

| 类别 | 倍率 |
|---|---:|
| cache read（命中） | **0.1×** |
| input（未命中） | 1× |
| cache write（本 session 是 1h TTL） | **2×** |
| **output** | **5×** |

### 三个被推翻的结论

1. **「长上下文每轮全价重发」是错的** —— 重发的部分绝大多数是 **cache read，只要 0.1×**。
   所以我先前算的「400k 单位/轮」高估了约 3–4 倍，实际一轮大约：
   `200k cache read ×0.1 = 20k` + `新增 input ~10k ×1` + `cache write ~10k ×2 = 20k`
   + `output ~2k ×5 = 10k` ≈ **60k input-等价**，再乘 Opus 倍率。

2. **`/clear` 的收益比我说的小** —— 而且它会**清空缓存**，之后重建上下文的头几轮要按 1× 全价付。
   净收益仍为正，但不是我吹的「20 倍」。

3. **真正最贵的是 output（5×），不是上下文长度。** 冗长的 subagent 报告、我啰嗦的回复，
   每个 token 值 10 个 cache-read token。

### 修正后的纪律（按杠杆从大到小）

1. **压 output**：subagent 完成报告要求「三行以内」；我的回复不铺排表格。
2. **压轮次**：一轮派多章。每轮都要付 cache write + output 的固定成本。
3. **别让缓存冷掉**：1h TTL —— session 闲置超过 1 小时，下一轮 200k 上下文要按 **1× 全价**
   重新付（等于 10 倍于命中态）。**长时间离开前 `/clear` 比留着热缓存划算**，
   短暂间隔则相反，留着更省。
4. 上下文长度本身是次要因素（0.1×），不必为它频繁清理。

### 校准数据不足

### 主 session 单轮成本（上下文 500k）

| 情形 | 计算 | OU | 占窗口 |
|---|---|---:|---:|
| 缓存命中 | 500k×0.1 + 新增 10k×1 + cache write 15k×2 + output 2k×5 | ~100k | **4.4%** |
| **缓存冷掉**（闲置 >1h） | 500k×1 + … | ~520k | **22%** |

→ 昨天那 22% 就是**一次冷缓存轮**。1h TTL 是硬拐点。

### 剩余 49 题的账

- subagent：49 × 28k token/题 = 1.37M raw；按 60% cache read / 25% 未命中 / 15% output
  加权 ≈ 0.53 OU/token → **726k OU ≈ 32% 窗口**
- 监工约 15–20 轮：
  - **不清上下文**：15 × 4.4% = **66%**（且任一次冷缓存 +22%）→ 合计 98%+，装不下
  - **清完**（上下文 ~20k）：15 × ~1% = **15%** → 合计 **47%，一个窗口内舒服做完**

### 结论：`/clear` 是决定性的

先前说「/clear 收益不大」是错的 —— 那时我按 200k 上下文估，实际是 **500k**。
